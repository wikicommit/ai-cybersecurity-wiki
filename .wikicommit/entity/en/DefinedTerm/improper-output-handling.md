Improper output handling is insufficient validation, sanitisation and handling of the outputs generated by large language models (LLMs) before they are passed downstream to other components and systems. It is entry LLM05:2025, "Improper Output Handling", of the 2025 edition of the [[DefinedTermSet/owasp-top-10-for-llm-applications|OWASP Top 10 for LLM Applications]]. Because LLM-generated content can be controlled by prompt input, the entry likens the behaviour to giving users indirect access to additional functionality. Successful exploitation can result in cross-site scripting (XSS) and cross-site request forgery (CSRF) in web browsers, and in server-side request forgery (SSRF), privilege escalation or remote code execution on backend systems.

## How it differs from overreliance

The entry separates improper output handling from overreliance: improper output handling deals with LLM-generated outputs before they are passed downstream, whereas overreliance focuses on broader concerns about overdependence on the accuracy and appropriateness of LLM outputs.

## What makes it worse

The entry lists conditions that can increase the impact of the vulnerability:

- the application grants the LLM privileges beyond what is intended for end users, enabling privilege escalation or remote code execution;
- the application is vulnerable to indirect [[DefinedTerm/prompt-injection|prompt injection]] attacks, which could allow an attacker to gain privileged access to a target user's environment;
- third-party extensions do not adequately validate inputs;
- output is not properly encoded for its context (for example HTML, JavaScript or SQL);
- LLM outputs are insufficiently monitored and logged;
- there is no rate limiting or anomaly detection for LLM usage.

## Examples

| Where the output goes | What can result |
| --- | --- |
| Directly into a system shell or a similar function such as `exec` or `eval` | Remote code execution |
| Back to a user as JavaScript or Markdown, which the browser interprets | XSS |
| SQL queries executed without proper parameterisation | SQL injection |
| File paths built without proper sanitisation | Path traversal |
| Email templates without proper escaping | Phishing attacks |

The entry's example attack scenarios include a chatbot's general-purpose LLM passing its response unvalidated to an extension with administrative functions, causing the extension to shut down for maintenance; a website summariser whose LLM follows a prompt injection on the page, encodes sensitive data from the site or the user's conversation and sends it, without output validation or filtering, to an attacker-controlled server; a chat feature that crafts SQL queries, where an unscrutinised query to delete all tables would delete them; and an LLM generating marketing email templates that an attacker manipulates into carrying malicious JavaScript. A further scenario concerns code generated from natural-language input, which risks exposing sensitive information, creating insecure data handling or introducing vulnerabilities such as SQL injection; the entry adds that the model may hallucinate non-existent software packages, potentially leading developers to download malware-infected resources, and calls thorough code review and verification of suggested packages crucial.

## Prevention

The entry's prevention and mitigation strategies are:

- treating the model as any other user, with a zero-trust approach, and applying proper input validation to responses coming from the model to backend functions;
- following the OWASP Application Security Verification Standard (ASVS) guidelines for effective input validation and sanitisation;
- encoding model output returned to users to mitigate undesired code execution by JavaScript or Markdown, for which the ASVS gives detailed guidance;
- context-aware output encoding based on where the output will be used, such as HTML encoding for web content and SQL escaping for database queries;
- parameterised queries or prepared statements for all database operations involving LLM output;
- strict Content Security Policies (CSP) to mitigate the risk of XSS from LLM-generated content;
- robust logging and monitoring to detect unusual patterns in LLM outputs that might indicate exploitation attempts.
