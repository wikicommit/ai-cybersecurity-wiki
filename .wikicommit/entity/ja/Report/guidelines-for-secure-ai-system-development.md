安全な AI システム開発のためのガイドライン（Guidelines for secure AI system development）は、一から構築されたものか、他者が提供するツールやサービスの上に構築されたものかを問わず、人工知能（AI）を使うあらゆるシステムのプロバイダーに向けたガイダンス文書である。英国国家サイバーセキュリティセンター（NCSC）と米国サイバーセキュリティ・インフラストラクチャセキュリティ庁（CISA）が国際的なパートナー機関の一団とともに公表しており、クラウン著作権の年は2023年となっている。その表明された目的は、意図したとおりに機能し、必要なときに利用でき、権限のない者に機密データを明かすことなく動作する AI システムを、プロバイダーが構築できるよう支援することである。

## 発行者と対象読者

NCSC と CISA のほかに、文書に名前が挙がっているパートナーには、米国連邦捜査局と国家安全保障局、オーストラリア、カナダ、ニュージーランド、フランス、ドイツ、エストニア、チェコ、ノルウェー、イスラエル、イタリア、シンガポール、韓国の政府のサイバーセキュリティ機関および情報機関、チリの Government CSIRT、ナイジェリアの国家情報技術開発庁、ポーランドのデジタル省と NASK 国立研究所、そして日本の2つの政府機関が含まれる。AI 企業、研究機関、大学などを含むさらなる組織の一覧が、その作成に貢献したものとして謝辞に挙げられている。

この文書は主に、組織がホストするモデルや外部のアプリケーションプログラミングインターフェース（API）を使う AI システムのプロバイダーを対象としているが、データサイエンティスト、開発者、管理者、意思決定者、リスクオーナーといったすべての利害関係者に一読を促している。すべてのガイドラインがすべての組織に当てはまるわけではなく、組織のユースケースと脅威プロファイルとあわせて検討すべきであると述べている。文書は TLP:CLEAR の扱いで公開されている。

## AI セキュリティを別扱いする理由

このガイドラインは「AI」という語を、ルールベースのシステムのような ML 以外の手法とは区別して、特に機械学習（ML）のアプリケーションを指すものとして用いている。ガイドラインによれば、AI システムは既存のサイバーセキュリティの脅威に加えて、新しい種類の脆弱性にさらされる。文書は、ハードウェア、ソフトウェア、ワークフロー、サプライチェーンを含む ML コンポーネントの根本的な脆弱性を悪用することを指して[[DefinedTerm/adversarial-machine-learning|敵対的機械学習]]（AML）という語を用いている。これにより攻撃者は、モデルの分類や回帰の性能に影響を与えたり、権限のない操作を行ったり、モデルの機密情報を抽出したりできる。文書が挙げる例は、大規模言語モデルに対する[[DefinedTerm/prompt-injection|プロンプトインジェクション]]攻撃と、訓練データやユーザーのフィードバックを意図的に汚染すること（[[DefinedTerm/data-poisoning|データポイズニング]]）である。

また文書は、AI のように開発が速く進む場合、セキュリティが二次的な考慮事項になりうるとし、そうではなくセキュリティをシステムのライフサイクル全体を通じた中核的な要件としなければならないと主張している。

## 責任を負うのは誰か

文書は、データの整備、アルゴリズムの開発、設計、デプロイ、保守に責任を負う「プロバイダー」と、入力を与えて出力を受け取る「ユーザー」という2つの当事者からなる単純なモデルを説明し、プロバイダーがサードパーティのソフトウェア、データ、モデル、サービスを組み込むようになるにつれて、このモデルは一般的ではなくなりつつあると指摘している。ユーザーは通常、自分が使うシステムのリスクを評価するための可視性や専門知識を欠いているため、文書は、セキュア・バイ・デザインの原則に沿って、AI コンポーネントのプロバイダーがサプライチェーンの下流にいるユーザーのセキュリティ上の結果に責任を負うべきだとしている。すなわち、可能な場合には制御を実装し、最も安全な選択肢をデフォルトにし、リスクを緩和できない場合には、下流のユーザーに対して彼らが受け入れるリスクを知らせ、安全な使い方について助言するということである。侵害によって有形の、または広範な物理的損害や評判の損害、事業運営の重大な損失、機密情報の漏洩、法的な影響が生じうる場合には、AI のサイバーセキュリティリスクを重大なものとして扱うべきであるとしている。

## ガイドラインの4つの領域

| 領域 | 対象とする範囲 | ガイドラインが求めることの例 |
| --- | --- | --- |
| 1. 安全な設計 | リスクの理解と[[DefinedTerm/threat-modeling\|脅威モデリング]]、システムとモデルの設計におけるトレードオフ | AI の脅威に対する職員の意識を高めること。システムへの脅威をモデル化すること。機能性だけでなくセキュリティも考慮して設計すること（サプライチェーンのデューデリジェンス、インポートしたサードパーティのモデルやシリアライズされた重みを信頼できないコードとして扱うこと、AI コンポーネントが引き起こせる操作を制限すること、最小権限を伴う安全なデフォルトを含む）。モデルを選定する際にセキュリティを比較衡量すること |
| 2. 安全な開発 | サプライチェーンのセキュリティ、文書化、資産と技術的負債の管理 | AI のサプライチェーンを保護すること（Supply Chain Levels for Software Artifacts などのリソースを参照）。モデル、データ、プロンプト、ログなどの資産を特定し、追跡し、保護すること。データ、モデル、プロンプトを文書化すること（たとえばモデルカード、データカード、ソフトウェア部品表を用いて）。技術的負債を管理すること |
| 3. 安全なデプロイ | 侵害、脅威、損失からのインフラストラクチャとモデルの保護、インシデント管理、責任あるリリース | アクセス制御と分離によってインフラストラクチャを保護すること。モデルの機能や訓練データを再構築しうる攻撃者からモデルを継続的に保護すること（モデルファイルやデータセットの暗号学的ハッシュや署名を共有することを含む）。インシデント管理の手順を策定すること。ベンチマークや[[DefinedTerm/red-team\|レッドチーミング]]などのセキュリティ評価を経てからのみリリースすること。安全な設定をデフォルトにすること |
| 4. 安全な運用と保守 | システムのデプロイ後の対応：ログ記録と監視、更新の管理、情報共有 | 分布外の入力や敵対的な入力の検知を含め、システムの振る舞いとその入力を監視すること。自動化された、セキュア・バイ・デザインの更新。情報共有のコミュニティに参加し、脆弱性の開示に応じて告知を公表すること |

機密性について、ガイドラインは、[[DefinedTerm/differential-privacy|差分プライバシー]]や準同型暗号といったプライバシー強化技術を、適切な場合には、リスクの水準を探ったり保証したりするために使えると述べている。

## 手法と整合性

このガイドラインは「セキュア・バイ・デフォルト」の手法をとっており、NCSC の Secure development and deployment guidance、米国国立標準技術研究所（NIST）の Secure Software Development Framework、そして CISA、NCSC、各国のサイバー機関が公表したセキュア・バイ・デザインの原則と密接に整合している。それらの原則は、顧客にとってのセキュリティ上の結果に責任を持つこと、徹底した透明性と説明責任を受け入れること、セキュア・バイ・デザインが事業の最優先事項となるよう組織の体制とリーダーシップを築くことを重視している。文書は、このガイドラインを、確立されたサイバーセキュリティ、リスク管理、インシデント対応の実務とあわせて検討すべきであるとしている。

参考文献の節は、AI 開発、サイバーセキュリティ、リスク管理に分類された関連資料を挙げている。その中には、NCSC の Principles for the security of machine learning、[[Project/hiroshima-ai-process|G7 広島AIプロセス]]のもとで作成された文書、MITRE ATLAS（ML システムに対する敵対者の戦術、技術、事例研究のナレッジベースで、[[DefinedTermSet/mitre-attack|MITRE ATT&CK]] をモデルとし、それと結びつけられていると説明されている）、NIST AI リスクマネジメントフレームワーク、AI モデルのセキュリティテストのためのオープンソースプロジェクトの一覧が含まれる。
