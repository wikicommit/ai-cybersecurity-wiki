PrimeVul は、脆弱性検出、すなわちある関数にセキュリティ上の脆弱性が含まれているかどうかを判定するタスクについて、コード言語モデル（code LM）を訓練・評価するためのデータセットである。論文 [[ScholarlyArticle/vulnerability-detection-with-code-language-models-how-far-are-we|Vulnerability Detection with Code Language Models: How Far Are We?]] で発表された。著者らがこれを構築したのは、既存の脆弱性データセットがデータ品質の低さ、ラベル精度の低さ、重複の多さを抱えており、それがモデル性能の信頼できない測定につながっていると判断したためである。著者らは PrimeVul を、人手で検証されたベンチマークに匹敵するラベル精度を、はるかに大きな規模で備えたものだと説明している。

## 内容

各サンプルは、脆弱または無害のラベルが付いた関数である。PrimeVul は関数の出どころとなったコミットのメタデータを保持しており、著者らはこれを使って関数の周辺のより広い文脈を抽出できると述べている。また、脆弱な関数とそのパッチ適用後のバージョンの組も含んでいる。

| 指標 | 値 |
| --- | --- |
| 脆弱な関数 | 6,968 |
| 無害な関数 | 228,800 |
| プロジェクト | 755 |
| コミット | 6,827 |
| 対象とする CWE | 140（SVEN の15.6倍） |
| SVEN と比較した脆弱な C/C++ 関数の数 | 16.7倍 |
| 脆弱と無害の比率 | およそ 1:32 |
| 脆弱–パッチ適用後の組 | 5,480 |

データは無作為にではなく、コミット日付によって分割されている。

| 分割 | 脆弱 | 無害 | 組になった脆弱 | 組になった無害 |
| --- | --- | --- | --- | --- |
| 訓練 | 5,574 | 178,853 | 4,354 | 4,354 |
| 開発 | 699 | 24,731 | 562 | 562 |
| テスト | 695 | 25,216 | 564 | 564 |

## 構築方法

PrimeVul は、既存の4つのデータセット——BigVul、CrossVul、CVEfixes、DiverseVul——に含まれるセキュリティ関連のコミットと、それらが変更した関数を出発点としている。CodeXGLUE（Devign）は、そのコミットのかなりの部分がセキュリティと無関係であることを著者らが見いだしたため、除外された。

- **重複除去**：変更された各関数は、スペース、タブ、改行、復帰文字を取り除いて正規化され、MD5 でハッシュ化される。コミット前とコミット後のバージョンのハッシュが同じ関数は変更なしとみなされて除かれ、セット全体にわたる重複もハッシュによって除去される。著者らは、その結果として訓練セットの脆弱な関数がテストセットに漏れ込むことはないと報告している。
- **ラベル付け**：関数を脆弱とみなす手法は2つある。*PrimeVul-OneFunc* は、その関数がセキュリティ関連のコミットによって変更された唯一の関数である場合に脆弱とする。*PrimeVul-NVDCheck* はコミットをその CVE エントリと結び付け、National Vulnerability Database の説明がその関数を名指ししている場合、またはそのファイルを名指ししていて、かつその関数がそのファイル内でコミットが変更した唯一の関数である場合に脆弱とする。これらの関数のコミット後のバージョンと、同じコミットで変更されなかったその他の関数は無害とラベル付けされる。基準を満たす関数を1つも含まないコミットは除外される。
- **品質確認**：著者らは、各ラベル付け手法から抽出した50件の脆弱な関数を手作業で確認した。正しくラベル付けされていたのは PrimeVul-OneFunc で86%、PrimeVul-NVDCheck で92%であり、手作業でラベル付けされた SVEN では94%であった。
- **組**：脆弱な関数はそのパッチと対応付けられ、2つのバージョンが文字列の80%以上を共有する、判定の難しい組だけが残された。パッチによって関数が削除されることもあるため、すべての脆弱な関数にパッチがあるわけではない。

## 評価での使い方

PrimeVul には、同じ論文で提案された評価ガイドラインが付属している。テストセットにはコミット日付で最も新しい10%のサンプルが収められている。そのため、モデルは過去のデータで訓練され、未来のデータでテストされる。また、1つのコミットに由来するサンプルが複数のセットに分かれることはない。モデルの採点には、Vulnerability Detection Score（VD-S）——偽陽性率を選んだ閾値（論文では0.5%）以下に抑えたときの偽陰性率——と、ペア単位の評価が使われる。ペア単位の評価では、脆弱–パッチ適用後の組について、モデルが両方の関数を正しくラベル付けしたか、両方を脆弱としたか、両方を無害としたか、それとも2つを逆にしたかを記録する。

この評価方法で評価されたモデルは、PrimeVul を発表した論文では低い成績にとどまった。StarCoder2 は、BigVul で訓練・テストした場合には F1 で68.26%に達したが、PrimeVul でテストした場合は3.09%、PrimeVul でファインチューニングした後でも18.05%だった。GPT-3.5 と GPT-4 は、組になった関数についてランダムな推測と変わらない成績だった。

## 限界とラベル付けの方針

著者らは、PrimeVul のラベル精度が100%に満たず、そのためデータのわずかな部分には誤ったラベルが付いていることを認めている。彼らのラベル付けは一部の先行研究より厳格である。関数は、それ単体でセキュリティリスクとなる場合にのみ脆弱とラベル付けされる。そのため、複数の関数にまたがる脆弱性に関わる関数や、修正との整合性を保つためだけに変更された呼び出し元の関数は、脆弱としては数えられない。
