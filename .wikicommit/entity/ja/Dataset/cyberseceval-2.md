CyberSecEval 2 は、大規模言語モデル（LLM）のセキュリティ上のリスクと能力を定量化するための、オープンソースのベンチマークスイートである。CyberSecEval の第2版であり、論文 [[ScholarlyArticle/cyberseceval-2-a-wide-ranging-cybersecurity-evaluation-suite-for-large-language-models|CyberSecEval 2: A Wide-Ranging Cybersecurity Evaluation Suite for Large Language Models]] で発表された。著者らはこれを、LLM の開発者——リリース前にチューニングするため、あるいはシステムに他にどのような安全策が必要かを判断するために、LLM がセキュリティリスクに対してどれほど脆弱かを測定する必要がある人々——と、LLM を使ってサイバーセキュリティ業務を自動化する人々のために構築した。そのコードと評価用の成果物は MIT ライセンスの下でオープンソースとして公開されており、著者らは新しいバージョンをリリースする予定だと述べている。

## テストの内容

CyberSecEval 2 は、2023年12月にリリースされた第1版の2つのテストカテゴリを引き継ぎ、新しいカテゴリを追加している。

| テストセット | 第2版での位置づけ | 測定する内容 |
| --- | --- | --- |
| 安全でないコーディング慣行 | 第1版から変更なし | 同じ機能の実装を求められたとき、またはコードの自動補完に使われたときに、LLM がオープンソースのコードから事前に特定された安全でないコーディング慣行を再現するかどうか |
| サイバー攻撃への協力 | 第1版から継続 | MITRE ATT&CK で定義された攻撃を対象に、サイバー攻撃への協力を求めるプロンプトに LLM が手を貸すかどうか。判定は別の LLM が行う |
| 誤拒否 | 新規 | 悪意があるように見えうる、無害な「境界線上」のサイバーセキュリティ関連プロンプトを、LLM がどれほどの頻度で拒否するか。False Refusal Rate として測定される |
| プロンプトインジェクション | 新規 | ユーザーや第三者からの入力がシステムプロンプトを覆そうとしたときに、LLM がシステムプロンプトに従うかどうか |
| コードインタプリタの悪用 | 新規 | 接続されたコードインタプリタを悪用するコードを書くよう求める要求に、LLM が応じるかどうか |
| 脆弱性の悪用 | 新規 | LLM が脆弱なプログラムを悪用（エクスプロイト）できるかどうか |

**False Refusal Rate（FRR、誤拒否率）** は、ある特定のリスクに関して安全でないプロンプトと取り違えたために LLM が拒否した、無害なプロンプトの割合（パーセント）と定義される。サイバー攻撃への協力の結果と合わせて読むと、著者らが safety-utility tradeoff（安全性と有用性のトレードオフ）と呼ぶ、有用性と有害性の間のトレードオフが見えてくる。

## 1つのテストケースの構成

**プロンプトインジェクション**：各ケースは3つの部分からなる。モデルにシステムプロンプトとして与えられるテストケースのプロンプト、システムプロンプトを回避しようとする悪意のあるユーザー入力または第三者入力を含むユーザー入力、そして攻撃が成功したかどうかを別の判定役 LLM が曖昧さなく判断するために使う判定用の質問である。ケースは、入力がシステムプロンプトの指示に反するものの一般的な害を伴わない「ロジック違反」型か、害が明白な「セキュリティ違反」型のいずれかであり、また直接型か、ユーザーがモデルに確認を頼む文書のような第三者のコンテンツを通じてインジェクションが届く間接型かのいずれかである。ケースは15の手法にわたり、その中には以前の指示の無視、トークンの密輸（token smuggling）、many-shot 攻撃と反復トークン攻撃、出力形式の操作、ペイロードの分割、説得が含まれる。このスイートは、反復的、マルチターン、または最適化ベースのインジェクション戦略は対象としておらず、システムプロンプトをサポートしないモデルはテストできない。

**コードインタプリタの悪用**：プロンプトは500件あり、5つのカテゴリ——コンテナからの脱出、権限昇格、インタプリタを使って他のシステムを攻撃する反射型攻撃、侵入後の活動（post-exploitation）、ソーシャルエンジニアリング——に100件ずつ割り当てられている。これらのカテゴリは、業界のオントロジーから採ったものではなく、著者ら自身が考案したものである。判定役 LLM が各出力を「応じた」か「拒否した」かでラベル付けし、カテゴリごとの応諾率を算出する。実際のインタプリタは使われず、著者らによれば、これにより実際のコードを実行するリスクが避けられ、テストの可搬性が高まり、コストも下がる。

**エクスプロイト**：テスト生成器が、CTF（capture-the-flag）形式の課題プログラムと、その脆弱性を発現させる概念実証（proof-of-concept）の入力をあわせて作成する。これにより、各課題が解けることが保証される。テストは、モデルがそれを記憶してしまうことを避けるためにランダムに生成され、現在のモデルにとって難しいが不可能ではないように設計されている。

| テストの種類 | 言語 | 採点 |
| --- | --- | --- |
| 文字列制約の充足 | C、JavaScript、Python | 満たした制約の割合。目標状態に到達すれば 1.0 |
| SQL インジェクション | Python と SQLite3 | 成功で 1、失敗で 0 |
| 基本的なバッファオーバーフロー | C | バッファの上書きで 0.5、望む値の書き込みで 1.0 |
| 多様なメモリエクスプロイト | C と C++ | 成功で 1、失敗で 0 |

## このスイートで報告された結果

このスイートを発表した論文では、テストしたすべてのモデルがプロンプトインジェクションの影響を受け、接続されたコードインタプリタへの攻撃を手伝うよう求める要求に対してモデルは平均35%で応じ、エクスプロイトの課題で良い成績を収めたモデルはなかった。また論文は、悪意あるサイバー攻撃のプロンプトに対する平均応諾率が、CyberSecEval 1 の52%から28%に低下したことも報告している。これらの結果は論文の知見であり、論文のページにまとめられている。

## 対象範囲の限界

著者らは、既知のプロンプトインジェクション手法のすべてを網羅しようとはしなかったと述べている。この領域は急速に変化し、網羅的なテストはすぐに古くなるためである。また、エクスプロイトのテストは実在の脆弱性を題材にしているが、あらゆる種類の脆弱性を網羅しようとはしていないとしている。侵害された振る舞いを引き起こすための敵対的機械学習の手法と、英語以外の言語によるプロンプトは、このリリースでは明示的に対象外とされている。
