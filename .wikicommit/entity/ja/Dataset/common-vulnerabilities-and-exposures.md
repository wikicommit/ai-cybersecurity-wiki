Common Vulnerabilities and Exposures（CVE）は、もともとは Common Vulnerability Enumeration と呼ばれていた仕組みで、公に知られている情報セキュリティ上の脆弱性と露出（exposure）を参照するための方法を提供する。米国国土安全保障省の National Cyber Security Division の資金提供を受け、MITRE Corporation が運営する、米国の Homeland Security Systems Engineering and Development Institute FFRDC によって維持されており、1999年9月に正式に一般向けに開始された。Security Content Automation Protocol は CVE を利用しており、CVE ID は MITRE のシステムに掲載され、米国の National Vulnerability Database（NVD）の基盤となっている。

## 目的

ソースが引用する言葉によれば、CVE は「公に知られている情報セキュリティ上の脆弱性に対する共通名（すなわち CVE 識別子）の辞書」である。共通の識別子があることで、別々のネットワークセキュリティのデータベースやツールの間でデータを共有しやすくなり、組織のセキュリティツールがどれだけを網羅しているかを評価する基準にもなる。CVE 識別子を記載した報告書があれば、読み手は CVE 互換のデータベースで修正情報をすばやく見つけられる。ある脆弱性に CVE 識別子を割り当てられた者は、関連するセキュリティ報告書、ウェブページ、電子メールにそれを記載することが推奨されている。また、調査の早い段階で識別子を取得しておけば、その後のやり取りや調整のすべてで、同じ脆弱性を曖昧さなく参照できる。

## CVE 識別子

MITRE の文書は、CVE 識別子（CVE 名、CVE 番号、CVE-ID、CVE とも呼ばれる）を、一般に公開されたソフトウェアパッケージに存在する、公に知られた情報セキュリティ上の脆弱性に対する一意の共通識別子と定義している。

- **形式**：1年に9,999件を超える ID に対応するため（「CVE10k 問題」）、2014年に構文が変更され、2015年1月13日に発効した。新しい構文は可変長の `CVE-YEAR-Arbitrary Digits` という形式で、固定の4桁を基本とし、ある暦年に必要になった場合にだけ桁数が増える（`CVE-YYYY-NNNN`、次に `CVE-YYYY-NNNNN`、以下同様）。この方式は、すべて4桁以上ある以前の ID と互換性を保っている。
- **候補**：識別子はもともと「候補」（`CAN-`）として始まり、エントリ（`CVE-`）に昇格できた。この慣行は2005年に廃止され、現在ではすべての識別子が CVE として割り当てられる。
- **ライフサイクル**：各エントリは*予約済み（reserved）*から始まる。セキュリティ上の脆弱性として受理されれば、正式な CVE エントリとして*公開（published）*される。基準を満たさないと判断された場合、たとえば脆弱性ではない問題に不適切に割り当てられていた場合や既存のエントリと重複している場合には、MITRE または CNA がそれを*却下（rejected）*の状態にできる。
- **対象範囲**：CVE は一般に公開されたソフトウェアを対象とし、広く使われているベータ版やプレリリース版を含みうるほか、商用ソフトウェアも含む。配布されないカスタムメイドのソフトウェアには、従来は CVE が割り当てられなかった。プログラムの最初の20年間は、サービス（ウェブベースの電子メールプロバイダなど）の脆弱性には、その問題が基盤となる一般配布のソフトウェア製品に存在しない限り CVE が割り当てられなかった。ただし MITRE を含む一部の CNA は、この変更に関する正式な規則を公表しないまま、2000年までさかのぼってサービスベースの脆弱性に CVE を割り当て始めている。

## 割り当てを行う者

CVE は CVE Numbering Authority（CNA）によって割り当てられる。一部のベンダーは、この名称と指定が2005年2月1日に設けられる以前から CNA として活動していた。割り当てには主に4つの種類がある。

| 割り当て元 | 役割 |
| --- | --- |
| The MITRE Corporation | 編集者および Primary CNA |
| ベンダー CNA（Microsoft、Oracle、HP、Red Hat など） | 自社製品に CVE 番号を割り当てる |
| CERT Coordination Center などの第三者コーディネーター | 他の CNA が対象としていない製品に CVE 番号を割り当てる |
| 研究者 | 1件の事例で CNA の役割を与えられた |

CVE 番号は、数日、数週間、数か月、場合によっては数年にわたって MITRE や NVD のデータベースに現れないことがある。その問題が公開禁止（エンバーゴ）の下にある（番号は割り当てられたが問題はまだ公になっていない）ためか、あるいは従来は MITRE にエントリを調査して記述するリソースが不足していたためである。

## レコードの内容

| フィールド | 内容 |
| --- | --- |
| Description | 問題についての標準化されたテキストによる説明。よく見られるエントリは「\*\* RESERVED \*\*」で、MITRE または CNA によって番号が予約されたときに表示される。たとえば CNA が番号のブロックを事前に要求した場合（Red Hat は500件単位のブロックで要求する）、問題が公になり MITRE が調査して記述するまでこの表示となる |
| Creation date | MITRE がエントリを作成した日付。CNA が割り当てた CVE についても同様である。事前に要求されたブロックの場合は、そのブロックが CNA に割り当てられた日付となる |

現在は使われていないフィールドとして、Phase（CAN または CVE）、Votes（候補を CVE にすべきかについての委員による投票）、Comments、Proposed（問題が最初に提案された時期）がある。MITRE のデータベースは CVE List Search で、NVD のデータベースはその CVE および CCE 脆弱性データベース検索で検索できる。

## 既知の問題

- **ベンダーの裁量**：CNA Rules の第7節の下では、脆弱性の報告を受けたベンダーはそれについて完全な裁量を持つ。これは利益相反を生みうる。ベンダーは自社の評判や金銭的利益を守るため、そもそも CVE の割り当てを拒否することがあり、MITRE はその決定を覆すことができない。2023年に発表された「!CVE」（not CVE）プロジェクトは、ベンダーに拒否された脆弱性のうち、プロジェクトの専門家パネルが有効と判断したものを収集している。
- **偽のエントリ**：偽の問題や、セキュリティ上の影響を伴わない問題に CVE 識別子が付与されたことがある。これを受けて、多くのオープンソースプロジェクトが自らのプロジェクトの CNA になることを申請した。

## 資金

2025年4月15日、翌日に期限を迎える MITRE と米国政府との契約が失効するに任されると報じられた。報道によれば、これにより新しい CVE の割り当てを含むプログラムの運用部門が終了する一方、データベースは GitHub を通じて引き続き利用可能になるとされた。失効の直前に契約は11か月延長され、停止は回避された。2026年3月16日に資金が失効するおそれが生じたのを受けて、CISA の長官代行はプログラムが現在では全額の資金を確保していると述べ、CVE Foundation の共同創設者は、その資金が裁量的な項目から、資金が手当てされる中核プログラムの一つへと再編されたと報告した。
