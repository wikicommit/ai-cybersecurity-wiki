過剰なエージェンシー（excessive agency）とは、大規模言語モデル（LLM）の予期しない、曖昧な、あるいは操作された出力に応じて、LLM の誤動作の原因が何であれ、損害をもたらす行動が実行されることを可能にしてしまう脆弱性である。[[DefinedTermSet/owasp-top-10-for-llm-applications|OWASP Top 10 for LLM Applications]] の2025年版の項目 LLM06:2025「Excessive Agency」にあたる。これは、開発者がある程度のエージェンシーを付与した LLM ベースのシステムで生じる。エージェンシーとは、プロンプトに応じて行動を起こすために、関数を呼び出したり、拡張機能（ベンダーによってツール、スキル、プラグインなどと呼ばれることがある）を通じて他のシステムと連携したりする能力である。

## LLM ベースのシステムにおけるエージェンシー

この項目によれば、どの拡張機能を呼び出すかの判断自体が LLM の「エージェント」に委ねられることがあり、エージェントは入力プロンプトや LLM の出力に基づいて動的にそれを決定する。エージェントベースのシステムは通常、LLM を繰り返し呼び出し、前の呼び出しの出力を用いて後の呼び出しの根拠づけと方向づけを行う。AI エージェント一般については[[DefinedTerm/ai-agent|AIエージェント]]を参照。

## 引き金と根本原因

この項目は、過剰なエージェンシーが損害へと変える誤動作の、よくある引き金として2つを挙げている。

- 設計の拙い善意のプロンプト、あるいは単に性能の低いモデルによって引き起こされるハルシネーションや作話
- 悪意あるユーザー、悪意ある拡張機能や侵害された拡張機能の以前の呼び出し、あるいはマルチエージェントシステムや協調型システムにおける悪意あるピアエージェントや侵害されたピアエージェントからの、直接的または間接的な[[DefinedTerm/prompt-injection|プロンプトインジェクション]]

その根本原因は通常、次の3つのうち1つ以上であり、項目は6つの例でこれを説明している。

| 根本原因 | 項目が挙げる例 |
| --- | --- |
| 過剰な機能 | エージェントの拡張機能が、システムに不要な機能を含んでいる。たとえば、リポジトリから文書を読み取るために選ばれたサードパーティの拡張機能が、文書の変更や削除もできる場合。開発中に試用され、より良いものに置き換えられた拡張機能が、エージェントから引き続き利用可能なままになっている場合。特定の1つのシェルコマンドを実行するための拡張機能が、他のシェルコマンドの実行を防げていない場合 |
| 過剰な権限 | データの読み取りを意図した拡張機能が、UPDATE、INSERT、DELETE の権限ももつ ID でデータベースに接続する場合。個々のユーザーに代わって動作するはずの拡張機能が、全ユーザーのファイルにアクセスできるアカウントなど、汎用的な高権限の ID で下流のシステムにアクセスする場合 |
| 過剰な自律性 | アプリケーションや拡張機能が、影響の大きい行動を独立に検証・承認しない場合。たとえば、ユーザーの確認をまったく得ずにユーザーの文書を削除する拡張機能 |

影響は機密性、完全性、可用性の全般に及びうるもので、LLM ベースのアプリケーションがどのシステムとやり取りできるかによって決まる。

この項目は、過剰なエージェンシーを、LLM の出力に対する精査の不十分さに関わる「安全でない出力処理」（insecure output handling）と区別している。

## 事例

この項目の攻撃シナリオ例では、LLM ベースのパーソナルアシスタントが、受信メールを要約できるよう、拡張機能を通じて個人のメールボックスへのアクセスを与えられる。開発者が選んだ拡張機能はメッセージの読み取りだけでなく送信もでき、またアプリケーションは間接プロンプトインジェクションに対して脆弱である。悪意をもって作られた受信メールが LLM を騙し、ユーザーの受信箱から機密情報を探して攻撃者のメールアドレスに転送するようエージェントに命令させる。項目によれば、これは、メールを読み取るだけの拡張機能にすること（過剰な機能の除去）、読み取り専用スコープの OAuth セッションでメールサービスに認証すること（過剰な権限の除去）、あるいは拡張機能が作成したすべてのメールをユーザーが確認して送信するよう求めること（過剰な自律性の除去）によって回避できた。一方、メール送信インターフェースへのレート制限は、損害を軽減するものである。

## 予防

この項目は、過剰なエージェンシーを防ぎうる8つの対策を挙げている。

| 対策 | 内容 |
| --- | --- |
| 拡張機能の最小化 | エージェントには必要な拡張機能だけを提供する。たとえば、URL を取得する必要のないシステムには URL 取得の拡張機能を与えない |
| 拡張機能の機能の最小化 | 拡張機能には必要な機能だけを実装する。たとえば、ユーザーのメールを要約する拡張機能には読み取り専用のアクセスだけを与える |
| 制約のない拡張機能の回避 | シェルコマンドの実行や URL の取得のような制約のない拡張機能よりも、粒度の細かい機能をもつ拡張機能を優先する。たとえば、シェル関数ではなく専用のファイル書き込み拡張機能を用いる |
| 拡張機能の権限の最小化 | 拡張機能には他のシステムに対して必要な権限だけを付与し、拡張機能が使う ID の権限によってそれを強制する。たとえば、単一の製品テーブルへの読み取りアクセスのみ |
| ユーザーのコンテキストでの拡張機能の実行 | ユーザーに代わって下流のシステムで行う行動は、そのユーザーのコンテキストで、必要最小限の権限で実行する。たとえば、最小スコープの OAuth を通じて |
| ユーザーの承認の要求 | ヒューマン・イン・ザ・ループの制御を用い、影響の大きい行動が実行される前に人間が承認するようにする。下流のシステムでも拡張機能内でもよい |
| 完全な仲介 | 行動が許可されるかどうかの判断を LLM に頼るのではなく、下流のシステムで認可を実装し、拡張機能を通じて行われるすべてのリクエストをセキュリティポリシーに照らして検証する |
| LLM の入出力のサニタイズ | OWASP Application Security Verification Standard（ASVS）などのセキュアコーディングの慣行に従い、特に入力のサニタイズに重点を置く。また、開発パイプラインで静的・動的・対話型のアプリケーションセキュリティテスト（SAST、DAST、IAST）を用いる |

さらに2つの対策は、過剰なエージェンシーを防ぐものではないが、損害を抑えることができる。望ましくない行動を特定するために拡張機能と下流のシステムの活動をログに記録して監視すること、そして一定期間に起こりうる望ましくない行動の数を減らすレート制限である。レート制限は、重大な損害が生じる前に監視によってそれらを発見できる可能性を高める。
