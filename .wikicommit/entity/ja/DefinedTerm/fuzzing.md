ファジング（ファズテスト）とは、プログラムに無効な、予期しない、あるいはランダムなデータを入力として与え、クラッシュ、コードに組み込まれたアサーションの失敗、潜在的なメモリリークといった例外が起きないかを監視する、自動化されたソフトウェアテスト手法である。ファザーは通常、ファイル形式やプロトコルのように、その構造によって有効な入力と無効な入力が区別される構造化入力を受け取るプログラムに対して用いられる。効果的なファザーは半ば有効な入力を生成する。すなわち、パーサーに即座に拒否されない程度には「十分に有効」でありながら、プログラムのより深い部分にある、適切に処理されていないコーナーケースに到達する程度には「十分に無効」な入力である。ファジングは主に、悪意をもって悪用されうる、セキュリティ上重要なプログラムの脆弱性を露呈させる自動化された方法として用いられる。

セキュリティの目的では、信頼境界を越える入力をファジングするのが最も有用であることが多い。特権ユーザーしか触れられない設定ファイルを解析するコードよりも、任意のユーザーがアップロードしたファイルを処理するコードをファジングするほうが重要である。

## 用語の由来

「ファズ（fuzz）」という用語は、ウィスコンシン大学で Barton Miller が教えていた大学院の上級オペレーティングシステムの授業（CS736）における1988年の授業課題に由来し、その結果は1990年に発表された。この課題では、UNIX のコマンドラインユーティリティの信頼性を試験するためにランダムな入力とコマンドライン引数を自動生成し、試験したユーティリティの25〜33パーセントをクラッシュさせた。Miller は、「ランダムで構造化されていないデータという感覚を呼び起こす」ためにこの名前を選んだと述べている。そのオラクルは意図的に単純で、プログラムはランダムな入力でクラッシュまたはハングすれば不合格、そうでなければ合格とされた。この初期の手法は、今日ではブラックボックス型、生成型、非構造化（「ダム」または「クラシック」）ファジングと呼ばれるものである。

ランダムな入力でプログラムをテストすることは、この用語よりも古い。その起源は1950年代にさかのぼり、当時プログラマーはゴミ箱から拾ったパンチカードや乱数のデッキをプログラムに与えていた。ランダムな入力を実行することは、ランダムテスト、モンキーテスト、モンテカルロデバッグとも呼ばれる。

## ファザーの種類

ファザーは、互いに独立した3つの観点で分類できる。

| 観点 | 種類 | 違い |
| --- | --- | --- |
| 入力の生成方法 | 生成型 / 変異型 | 生成型ファザーは（たとえばユーザーが与えた入力モデルから）入力をゼロから構築し、シードコーパスに依存しない。変異型ファザーは、libpng をファジングする際の有効な PNG ファイルのような、既存のシード入力のコーパスを改変する。両方を行うファザーもある |
| 入力構造の認識 | ダム（非構造化） / スマート（構造化） | スマート（モデルベース、文法ベース、プロトコルベース）ファザーは入力モデルを用いて有効な入力をより高い割合で生成するが、通常そのモデルを与える必要がある。ダムファザーはモデルを必要としないため、より多くのプログラムに適用できるが、有効な入力の生成は少なくなりがちで、主にパーサーに負荷をかける。たとえば、正しい CRC チェックサムを生成する可能性は低い |
| プログラム構造の認識 | ブラックボックス / グレーボックス / ホワイトボックス | ブラックボックスファザーは内部構造を無視し、毎秒数百の入力を実行して容易にスケールするが、「浅い」バグしか見つけられないことがある。ホワイトボックスファザーは記号実行などのプログラム解析を用いて深いコードや重要なコードに到達するが、解析時間のコストがかかる。グレーボックスファザーは、プログラム解析の代わりに軽量な計装を用いて、各入力が達成するカバレッジを把握する |

グレーボックスファジングのよくある形態は、カバレッジガイド型ファジングである。ファザーは以前の実行から得たカバレッジ情報を用いて新しい入力を導き、これまでに見られなかった振る舞いを生む入力をコーパスに保持し、さらに変異させてより多くの実行パスを発見する。ファザーは実行しないコードのバグを明らかにすることはできないため、一般に、達成するコードカバレッジが高いほど効果的だとみなされる。たとえば、[[SoftwareApplication/american-fuzzy-lop|AFL]] や libFuzzer は軽量な計装を用いて、入力が実行する基本ブロック間の遷移を追跡し、妥当な性能コストでコードカバレッジの増加をファザーに知らせる。

## 仕組み

正確なワークフローは手法や実装によって異なるが、一般的なファジングのワークフローは5つの段階からなる。

1. **準備** — ファザーとファズターゲット（ソフトウェアやライブラリ）を選び、既存のテスト入力や手作りの入力からシードコーパスを用意する。必要に応じて、興味深いトークンの辞書も用意する。
2. **入力の生成と変異** — ファザーがシードから新しいテストケースを作る。
3. **実行** — 生成された各入力でターゲットを実行する。ターゲットは、特定の種類のプログラミングエラーを検出するために、AddressSanitizer や UndefinedBehaviorSanitizer などのサニタイザー付きでビルドされることが多い。
4. **フィードバックとカバレッジ** — フィードバックガイド型のファザーは、コードカバレッジなどのシグナルを用いて今後の入力を誘導し（すべてのファザーがそうするわけではない）、新しい振る舞いに到達した入力を保持する。
5. **反復** — より多くのプログラムの振る舞いを探索するために、このプロセスを繰り返す。

### 障害の検出

ファザーは期待どおりの振る舞いとバグのある振る舞いを見分けなければならない。これは自動テストにおいてテストオラクル問題と呼ばれる。仕様がない場合、ファザーは通常、クラッシュする入力としない入力を分ける。クラッシュはサービス拒否や任意コード実行のような脆弱性を示している可能性があるが、クラッシュしないことは脆弱性がないことを示さない。C のプログラムはバッファオーバーフローでクラッシュすることもあれば、しないこともある。サニタイザーは、障害が検出されたときにプログラムをクラッシュさせるアサーションを注入することで、ファザーがクラッシュ以外のものにも反応できるようにする。

| サニタイザー | 検出するもの |
| --- | --- |
| AddressSanitizer（メモリデバッガ） | バッファオーバーフローや解放後使用（use-after-free）などのメモリエラー |
| ThreadSanitizer | 競合状態とデッドロック |
| UndefinedBehaviorSanitizer | 未定義動作 |
| LeakSanitizer | メモリリーク |
| CFISanitizer | 制御フロー完全性の違反 |

ファジングは「差分」バグを見つけることもできる。回帰テストでは同じ入力をプログラムの2つのバージョンで実行し、差分テストでは同じプログラムの2つの実装（2つのウェブサーバーなど）で実行する。出力の違いがバグの候補を示す。

### ツールチェーン

ファザーは非常に多くの入力を生成するため（2016年には Google の [[SoftwareApplication/oss-fuzz|OSS-Fuzz]] が週に約4兆の入力を生成した）、多くのファザーにはその後の作業を自動化するツールチェーンが付属している。

- **自動バグトリアージ**は、障害を引き起こす入力を根本原因ごとにグループ化し、バグを深刻度によって順位づける。CERT コーディネーションセンターの Linux 向けトリアージツールは、クラッシュする入力をスタックトレースでグループ化し、悪用可能である可能性の高さによってグループを並べる。Microsoft の「!exploitable」ツールは、クラッシュする入力をハッシュ化してその一意性を判定し、Exploitable、Probably Exploitable、Probably Not Exploitable、Unknown のいずれかに評価する。
- **自動入力最小化**（テストケース縮小）は、バグを再現したまま、障害を引き起こす入力をできるだけ削る。Delta Debugging は拡張された二分探索でこれを行う。
- **継続的ファジング**は、ソフトウェアの変更に合わせてファズターゲットを繰り返しビルドして実行する。OSS-Fuzz のようなサービスは、新たに見つかったバグをメンテナーに報告し、後で修正を検証する。

## セキュリティでの利用

| 時期 | 出来事 |
| --- | --- |
| 2012年4月 | Google が、Chromium ウェブブラウザのセキュリティ上重要なコンポーネントのためのクラウドベースのファジング基盤 ClusterFuzz を発表した。研究者は自作のファザーをアップロードし、クラッシュを見つけるとバグ報奨金を受け取れる |
| 2014年9月 | Bash シェルのセキュリティバグ群 Shellshock が公表された。その脆弱性のほとんどはファザー AFL で見つかった |
| 2015年4月 | Hanno Böck が、2014年の OpenSSL の Heartbleed 脆弱性を AFL がどのように発見できたかを示した |
| 2016年8月 | DARPA が、初の Cyber Grand Challenge の決勝を開催した。これは完全に自動化されたキャプチャー・ザ・フラッグ競技で、相手のソフトウェアの欠陥を発見する攻撃戦略としてファジングが用いられた。優勝したシステム「Mayhem」はチーム ForAllSecure が開発した |
| 2016年9月 | Microsoft が、クラウドベースのファズテストサービス Project Springfield を発表した |
| 2016年12月 | Google が、セキュリティ上重要なオープンソースプロジェクトを継続的にファジングする OSS-Fuzz を発表した |
| 2018年 | Black Hat で Christopher Domas が、ファジングを用いて、セキュリティチェックを回避して Ring 3 から Ring 0 の命令を実行できる、プロセッサ内の隠された RISC コアを暴いた |
| 2020年9月 | Microsoft が、Windows と Linux 向けのセルフホスト型の Fuzzing-as-a-Service プラットフォーム OneFuzz を公開した。2023年11月1日にアーカイブされた |

現代のウェブブラウザは大規模なファジングを受けている。Chrome Security Team は15,000コアで Chromium のコードを継続的にファジングしており、Microsoft は開発中に Microsoft Edge（Legacy）と Internet Explorer を670マシン年にわたってファジングし、10億の HTML ファイルから4,000億を超える DOM 操作を生成した。また、ファジングを動的解析と組み合わせることで、報告された問題を実際に引き起こす入力の生成を試み、静的解析の報告を検証することもできる。

## 限界

ファジングはバグの存在を示すものであって、その不在を示すものではない。何週間ファジングしても何も見つからないことは、プログラムの正しさを証明しない。あらゆる入力に対する正しさを証明するには、形式仕様と形式手法が必要である。

標準的なファジングには実用上の限界もある。複雑なソフトウェアに対しては、不要な、あるいは質の低いテストケースを大量に生成しうる。研究者らはこれに対処してコードカバレッジを高めるために深層学習の手法を取り入れているが、さらなる研究がなお必要である。ファジングツールは、サイバーフィジカルシステム、機械学習システム、そして振る舞いが訓練データによって決まるシステムでは苦戦することがある。ファザーは、タイミング、キャッシュの振る舞い、エネルギー消費に関わるサイドチャネル漏洩、権限昇格、論理エラーなど、クラッシュを引き起こさないセキュリティ上重要な欠陥を見逃すことがあり、複雑な条件に守られたバグに到達するには人間の介入が必要になることがある。
