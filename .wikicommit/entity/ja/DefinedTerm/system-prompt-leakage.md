システムプロンプトの漏洩（system prompt leakage）とは、大規模言語モデル（LLM）の振る舞いを制御するために使われるシステムプロンプトや指示に、発見されることを意図していない機密情報が含まれているリスクである。[[DefinedTermSet/owasp-top-10-for-llm-applications|OWASP Top 10 for LLM Applications]] の2025年版の項目 LLM07:2025「System Prompt Leakage」にあたる。システムプロンプトは、アプリケーションの要件に沿ってモデルの出力を導くように設計されるが、意図せず秘密情報を含んでしまうことがある。その情報は、発見されると他の攻撃を容易にするために使われうる。

## 本当のリスクはどこにあるか

この項目は、システムプロンプトを秘密とみなすべきではなく、セキュリティ管理策として用いるべきでもないと強調しており、したがって認証情報や接続文字列のような機密データをシステムプロンプトに書き込むべきではないとしている。この項目の見方では、システムプロンプトそのものが開示されることは本当のリスクではない。リスクはその根底にある要素、つまり[[DefinedTerm/sensitive-information-disclosure|機密情報の漏洩]]、システムのガードレールの回避、権限の不適切な分離などにある。システムプロンプトがロールや権限を記述していたり、接続文字列やパスワードを保持していたりする場合、根本的な問題はそれらが開示されることではなく、アプリケーションが強固なセッション管理と認可チェックを LLM に委ねていること、そして機密データが保存されるべきでない場所に保存されていることである。

この項目はさらに、正確な文言が開示されなくても、アプリケーションを使い、モデルに発話を送ってその結果を観察する攻撃者は、システムプロンプトに含まれるガードレールや書式上の制約の多くをほぼ確実に突き止められると付け加えている。

## とりうる形態

| 例 | システムプロンプトが明らかにするものと、攻撃者によるその利用 |
| --- | --- |
| 機密性の高い機能の露出 | 機密性の高いシステムアーキテクチャ、API キー、データベースの認証情報、ユーザートークンなど、秘密にしておくべき情報や機能。攻撃者はこれらを抽出したり、アプリケーションへの不正アクセスに利用したりできる。たとえば、あるツールが使用するデータベースの種類がわかれば、攻撃者はそれを SQL インジェクションの標的にできる |
| 内部ルールの露出 | 銀行のチャットボットにおける1日の取引上限額や最大融資額など、内部の意思決定プロセス。攻撃者はこれによってアプリケーションの仕組みを把握し、弱点を突いたり、設定された上限を超えて取引するなど管理策を回避したりできる可能性がある |
| フィルタリング基準の暴露 | 他のユーザーに関する情報の要求は常に拒否するといった、機密性の高いコンテンツをフィルタリングまたは拒否するための指示 |
| 権限とユーザーロールの開示 | どのロールがユーザー記録を変更する完全なアクセス権を与えるかといった、アプリケーション内部のロール構造や権限レベル。これを知った攻撃者は、権限昇格攻撃を狙える可能性がある |

この項目が示す二つの攻撃シナリオの例では、一つ目は、漏洩したシステムプロンプトに LLM がアクセスできるツールの認証情報が含まれており、攻撃者がそれを他の目的に利用するものである。二つ目は、攻撃者が、攻撃的なコンテンツ、外部リンク、コード実行を禁止するシステムプロンプトを抽出し、その後[[DefinedTerm/prompt-injection|プロンプトインジェクション]]攻撃を用いてそれらの指示を回避し、リモートコード実行を容易にするものである。この項目は、このリスクを MITRE ATLAS の技術 AML.T0051.000、LLM Prompt Injection: Direct（Meta Prompt Extraction）と関連づけている。

## 防止

この項目が示す四つの防止・緩和策は、いずれも制御をシステムプロンプトの外へ移すものである。

- **機密データをシステムプロンプトから分離する** — API キー、認証キー、データベース名、ユーザーロール、アプリケーションの権限構造などの機密情報をシステムプロンプトに埋め込まず、モデルが直接アクセスしないシステムに外部化する。
- **厳密な振る舞いの制御をシステムプロンプトに頼らない** — LLM はシステムプロンプトを改変しうるプロンプトインジェクションなどの攻撃を受けやすいため、可能な限り LLM の外部にあるシステムに頼る。たとえば、有害なコンテンツの検知と防止は外部のシステムで行うべきである。
- **ガードレールを LLM の外部に実装する** — システムプロンプトを明かさないようモデルを訓練することは有効でありうるが、モデルが常にそれに従う保証にはならない。そのため、システムプロンプトでの指示よりも、出力が要件に適合しているかを検査する独立したシステムのほうが望ましい。
- **セキュリティ管理策を LLM から独立して適用する** — 権限の分離や認可の境界チェックといった重要な管理策は、決定論的かつ監査可能な方法で行われる必要があるため、システムプロンプトを通じてであれ他の方法であれ、LLM に委ねてはならない。この項目によれば、LLM は（現時点では）そうした方法に適していない。エージェントのタスクに異なるレベルのアクセスが必要な場合は、複数のエージェントを用い、それぞれに必要最小限の権限を設定すべきである。
