「Fuzz4All: Universal Fuzzing with Large Language Models」（Fuzz4All：大規模言語モデルによる汎用ファジング）は Fuzz4All を提示する論文である。著者らはこれを、多くの異なる入力言語と、それらの言語の多くの機能を対象にできるという意味で汎用的な、初めてのファザーと説明している。論文の定義によれば、[[DefinedTerm/fuzzing|ファジング]]とは、テスト対象システムのクラッシュなどの予期しない振る舞いを露呈させるよう設計された入力を生成する、自動化されたテスト手法である。論文が対象とするのは、プログラミング言語や形式言語を入力として受け取るシステム、すなわちコンパイラ、ランタイムエンジン、制約ソルバー、アクセス可能な API を持つライブラリである。論文はこれらをソフトウェア開発の基本的な構成要素と呼んでいる。コンパイラやランタイムエンジンのバグは、その上に構築されたあらゆるアプリケーションに影響しうるからである。

この論文は、2024年4月14日から20日にリスボンで開催された 2024 IEEE/ACM 46th International Conference on Software Engineering（ICSE '24）で発表され、DOI は 10.1145/3597503.3639121 である。このページが依拠する arXiv 版は 2308.04748 の第3版で、2024年12月9日付である。著者は University of Illinois Urbana-Champaign の Chunqiu Steven Xia、Jia Le Tian、Lingming Zhang と、University of Stuttgart の Matteo Paltenghi、Michael Pradel である。

## 扱う問題

論文は従来のファザーを、たとえば対象言語のあらかじめ定義された文法から完全な入力を合成する生成ベースのファザーと、高品質なシードの集合に変異演算子や変換規則を適用する変異ベースのファザーに分けている。そして、両者に共通する3つの限界を挙げている。

| 限界 | 論文による説明 |
| --- | --- |
| 対象システムと言語への密結合 | ファザーは通常1つの言語やシステムのために作られ、作るのに時間がかかる。C/C++ コンパイラのファザーである Csmith は8万行を超えるコードからなり、その労力を別の言語に再利用するのは難しい |
| 進化への対応の欠如 | ある言語のあるバージョンのために設計されたファザーは、新しいバージョンでは有効性を失うことがある。Csmith は C++11 までの機能しかサポートしておらず、論文は、6か月間のファジング期間に最新の GCC と Clang のリリースで新たなバグを1つも発見しなかったとする先行研究を引用している |
| 限られた生成能力 | 生成ベースのファザーは言語の文法の一部しか使わないことが多く、変異ベースのファザーは変異演算子によって制約され、高品質なシードを必要とする |

論文はさらに、AFL や libFuzzer などの汎用ファザーは対象言語を意識しない単純なバイト単位の変異を用いるため、プログラムを入力として受け取るシステムに対して有効な入力を生成する可能性は極めて低いと付け加えている。

## Fuzz4All の仕組み

Fuzz4All の中心的なアイデアは、大規模言語モデル（LLM）を入力の生成・変異エンジンとして使うことである。論文の主張によれば、LLM は多くの言語の大量のコードで事前学習されているため、それらの言語の構文と意味を暗黙的に理解している。ユーザーは、テスト対象システムを説明する文書（ドキュメント、サンプルコード、仕様）と、任意で、重点を置く特定の機能を与える。この手法には2つの主要なステップがある。

- **オートプロンプティング。** 大きな「蒸留」用 LLM（実装では GPT-4）が、ユーザーの入力を要約して候補プロンプトを作る。温度0での貪欲サンプリングで1つ、多様性のためにより高い温度でさらに複数を作る。各候補は生成用 LLM を使った小規模なファジング実験で試され、システムが有効として受け入れる一意な入力を最も多く生んだプロンプトが残される。論文の例では、C++23 の機能 std::expected についての cppreference のドキュメント498語を、214語のプロンプトに蒸留している。
- **ファジングループ。** より小さな「生成」用 LLM（StarCoder）が、ファジング入力をバッチ単位で生成する。各反復の前に、Fuzz4All は直前のバッチから有効な入力を1つ例としてプロンプトに付け加え、さらに3つの生成指示のうち1つを無作為に選んで付け加える。その3つとは、新しい入力を生成する、例を変異させる、例と意味的に等価な入力を作る、である。これらの戦略は、生成ベースのファザーによる合成と、変異ベースのファザーによる変種の作成をモデルにしている。すべての入力はシステムに対して実行され、ユーザーが定義するオラクルによってチェックされる。論文では、セグメンテーション違反によるクラッシュや内部アサーションの失敗などの単純なオラクルを使っている。

2つのモデルを使うのはコストのトレードオフである。任意のユーザー入力を理解するには高性能なモデルが必要だが、それを生成に使うのは推論コストのために非効率になる。Fuzz4All はテスト対象システムの計装を必要とせず、オートプロンプティングとファジングループのコンポーネントは872行の Python からなる。

## 何を行ったか

著者らは Fuzz4All を、6つの言語を入力とする9つのテスト対象システムで評価し、それぞれをその言語の最先端のファザーと比較した。

| 言語 | テスト対象システム | ベースラインのファザー |
| --- | --- | --- |
| C | GCC, Clang | GrayC, Csmith |
| C++ | G++, Clang++ | YARPGen |
| SMT2 | Z3, CVC5 | TypeFuzz |
| Go | Go | go-fuzz |
| Java | javac | Hephaestus |
| Python | Qiskit（量子コンピューティングプラットフォーム） | MorphQ |

カバレッジは、言語ごとに1つのシステムで、5回繰り返した24時間のキャンペーンにより比較され、統計的有意性は Mann-Whitney の U 検定で検定された。その後の実験では、生成入力1万件という予算を使った。論文は、行カバレッジ、生成された入力の有効率、ターゲットファジングのヒット率（対象の機能を使っている入力の割合で、単純な正規表現でチェックされる）、そして発見されたバグの数を報告している。

## 要点

- 24時間のキャンペーンの終了時点で、Fuzz4All はすべての対象で最も高いカバレッジを達成した。最も成績の良いベースラインに対する平均の改善は36.8%で、改善幅は13.7%（Go）から75.6%（Qiskit）までの範囲にあった。すべての改善が統計的に有意とされた。
- Fuzz4All の入力は、ベースラインのものよりも有効である割合が低く（有効率は平均56.0%低下）、数も少なかった（生成が GPU 推論によってボトルネックになるため43.0%少ない）。しかし著者らは、カバレッジが示すとおりそれらの入力ははるかに多様であり、有効に近い無効な入力でもシステムの検証ロジックのバグを見つけうると論じている。
- 24時間以内にカバレッジが頭打ちになったベースラインと異なり、Fuzz4All はキャンペーンの終盤でも新たなコードをカバーし続けた。著者らは、各反復で新しい例と戦略によってプロンプトを更新することがその理由だと推測している。
- ターゲットファジングは機能した。単一の機能のドキュメントを与えた場合、生成された入力の平均83.0%がその機能を使っていた。一方、汎用的なファジングのヒット率は平均で96.0%低かった。Qiskit では3つの対象機能すべてで0%であり、著者らはこれを、それらの機能が新しく、LLM の学習データにまれにしか現れないためとしている。
- アブレーション研究では、オートプロンプティングによってユーザーの入力を蒸留すると、初期プロンプトを使わない場合や生のドキュメントを使う場合のいずれよりも高いカバレッジが得られ、ファジングループに例を加え、さらに3つの生成戦略すべてを加えるとカバレッジがさらに上がった。完全な手法では入力の4.7%が重複していたのに対し、例を伴わずに同じプロンプトからサンプリングした場合は8.0%だった。
- Fuzz4All は9つのシステム全体で98件のバグを発見し、そのうち64件は開発者によって未知のものと確認された。例としては、noexcept 機能を使った有効なコードによって引き起こされた GCC の内部コンパイラエラー（開発者が修正し、改変した形で GCC のテストスイートに追加した）や、Qiskit の QASM エクスポーターのバグ（著者らによれば、テンプレートに基づく先行研究では見つけられなかったもの）がある。

## 著者らが述べる限界

内的妥当性に対する主な脅威は Fuzz4All の実装の正しさで、コードレビューとテストによって対処している。外的妥当性に対する主な脅威は評価対象の選択で、6つの言語にわたる9つのシステムと繰り返し実行によって対処している。生成用 LLM の知識は学習データに由来するため、まったく同じ StarCoder のチェックポイントを使い続けると、データの変化（data shift）によって時間とともに有効性が下がるかもしれない。著者らは、最新のドキュメントを用いたオートプロンプティングでこれを緩和できると述べている。また、蒸留用 LLM はハルシネーションを起こす可能性があり、著者らはこれが LLM を使うほとんどのパイプラインに共通する限界だと注記している。

## 先行研究との関係

論文は Fuzz4All を、いくつかの系統の先行研究と対比している。PolyGlot のような言語非依存の手法も、依然として言語固有の文法でシードを解析し、限られた変異の集合を使う。それ以前の学習ベースのファザーは言語固有のモデルを学習しており、LLM を使って深層学習ライブラリをファジングする TitanFuzz は、手作りのプロンプトと変異パターンに依存しているため、他のシステムへ容易に拡張することができない。LLM ベースの単体テスト生成器は、関数のソースコードのような特定の種類の入力を必要とし、単体テストにしか使えない。プロンプティングについては、著者らは自らのオートプロンプティングを、知る限り、LLM へのブラックボックスのサンプリングアクセスだけでソフトウェア工学のタスクのために任意のユーザー入力を蒸留する初めての手法であり、各プロンプトを代理指標ではなく有効な入力を生成するという実際のタスクで評価するものだと説明している。
