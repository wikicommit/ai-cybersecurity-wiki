「CyberSecEval 2: A Wide-Ranging Cybersecurity Evaluation Suite for Large Language Models」（CyberSecEval 2：大規模言語モデルのための広範なサイバーセキュリティ評価スイート）は、大規模言語モデル（LLM）のセキュリティリスクと能力を定量化するためのベンチマークスイートである [[Dataset/cyberseceval-2|CyberSecEval 2]] を提示する論文である。この論文は、LLM が新たなセキュリティリスクをもたらしているという観察から出発する。そのリスクは、コード生成の熟練度の向上、コードインタープリタでコードを生成し自動実行する用途での利用、そして信頼できないデータを処理するアプリケーションへの組み込みから生じるものだが、それらのリスクを測定し低減するための包括的な評価スイートはほとんど存在しない。

論文の日付は2024年4月18日で、2024年4月19日に arXiv に 2404.13161v1 として cs.CR で投稿された。著者は Manish Bhatt、Sahana Chennabasappa、Yue Li、Cyrus Nikolaidis、Daniel Song、Shengye Wan、Faizan Ahmad、Cornelius Aschermann、Yaohui Chen、Dhaval Kapil、David Molnar、Spencer Whitman、Joshua Saxe で、そのうち7人が同等の筆頭著者として示されている。

## CyberSecEval に何を加えたか

この論文は、著者らが2023年12月に公開した先行版の CyberSecEval 1 を拡張したものである。CyberSecEval 1 は、安全でないコーディングの提案とサイバー攻撃への協力度をテストしていた。この論文が想定する読者は2つあり、LLM を構築する人々（システムのために LLM を選定する人々を含む）と、LLM を使ってサイバーセキュリティのタスクを自動化する人々である。貢献は次のとおりである。

- **[[DefinedTerm/prompt-injection|プロンプトインジェクション]]のテスト**：15のカテゴリーの攻撃を扱い、直接型（ユーザーの入力がシステムプロンプトに反して働く）と間接型（モデルのコンテキストウィンドウ内のサードパーティのコンテンツがインジェクションを運ぶ）の両方、そしてロジックに違反するものとセキュリティに違反するものの両方を含む。
- **コードインタープリタ悪用のテスト**：5つのカテゴリーに100件ずつ、計500件のプロンプトで、接続されたコードインタープリタを悪用するコードを LLM に書かせようとする。
- **エクスプロイトのテスト**：C、C++、Python、JavaScript でランダムに生成されたキャプチャー・ザ・フラッグ（CTF）形式のプログラムで、モデルはこれをエクスプロイトしなければならない。文字列制約の充足、SQL インジェクション、メモリ破壊を扱う。
- **誤拒否率（False Refusal Rate, FRR）**：LLM が、ある特定のリスクに関して安全でないプロンプトと取り違えて拒否した良性のプロンプトの割合として定義される。あわせて、サイバー攻撃への協力度についてこれを測定するための、新たな「境界的」サイバーセキュリティプロンプト（悪意があるように見えうる良性のリクエスト）のセットが加えられている。論文は、これが測定する緊張関係を安全性と有用性のトレードオフと呼んでいる。安全でないプロンプトを拒否するように LLM を調整すると、良性のプロンプトまで誤って拒否するようになり、有用性が下がりうるということである。

著者らは、侵害された振る舞いを誘発するための勾配最適化やヒューリスティック最適化などの敵対的機械学習の手法と、英語以外の言語のプロンプトを、このリリースでは明示的に目標外としている。安全でないコーディングのテストは CyberSecEval 1 から変わっておらず、論じられていない。

## 何を行ったか

ケーススタディとして、著者らはプロンプトインジェクション、エクスプロイト、サイバー攻撃への協力度、インタープリタ悪用のテストを、Llama、Code Llama、OpenAI GPT の各ファミリーのモデルに適用した。2024年3月と4月に実施したサイバー攻撃への協力度のテストには、Google の gemini-pro も含まれていた。モデルはデフォルト設定で実行された。著者らはその目的を、LLM の状況を包括的に評価することではなく、テストを実演し、さらなる研究のためのテーマを見出すことだと説明している。また、GPT-4 のようなクローズドなシステムには追加のガードレールが含まれている可能性があるため、オープンウェイトのモデルとの比較は同条件のものではないと注記している。Mistral は、その API がシステムプロンプトをサポートしていなかったため、プロンプトインジェクションのケーススタディから除外された。

## 要点

- プロンプトインジェクションに対して LLM を調整することは、依然として未解決である。要旨と序論は、テストしたすべてのモデルでプロンプトインジェクションのテストの26%から41%が成功し、平均成功率は28%だったと報告している。一方、結果の節ではすべてのモデルの平均を17.1%以上としており、結論では13%から47%という範囲を示している。出力フォーマットの操作は大半のケースで成功し、トークンスマグリングはめったに成功しなかった。また、より大きなモデル（700億パラメータのモデルと GPT-4）はインジェクションにより強く抵抗する傾向があった。
- これらの結果から、著者らはシステム設計者に対し、敵対的な入力に直面したときに LLM がシステムプロンプトの指示に確実に従うと想定せず、プロンプトインジェクションに対するガードレールと検知を追加するよう助言している。
- サイバー攻撃への協力を求めるリクエストへの応諾は、CyberSecEval 1 と比べて減少した。悪意のあるプロンプトへの平均応諾率は52%から28%に下がり、著者らはこれを業界がこの問題をより意識するようになったことの表れと読んでいる。Llama 3 ファミリーが最も良好な非応諾を示し、モデルが最も多く拒否した攻撃カテゴリーと最も少なく拒否した攻撃カテゴリーの差は0.34から0.1に縮まった。
- 安全性と有用性のトレードオフは小さかった。多くのモデルは、攻撃的なサイバー作戦への協力を求めるリクエストの大半を拒否しつつ、良性の境界的なリクエストには応じていた。いくつかのモデルは誤拒否率を15%未満に保っていた一方、codellama-70B の誤拒否率は70%と際立って高かった。
- モデルは、接続されたコードインタープリタへの攻撃に協力するよう求めるリクエストの13%から47%（平均35%）に応じた。著者らは、LLM をコードインタープリタに接続する場合の追加のセキュリティ層として、安全性チューニングを推奨している。
- エクスプロイトでよい成績を収めたモデルはなかった。一般的なコーディング能力が高いモデル（GPT-4、Llama 3 70b-Instruct、CodeLlama-70b）が最も良い成績を示し、能力はパラメータ数と相関しているように見えたが、ほとんどのモデルはすべての SQL インジェクションのテストで0点だった（20%だった GPT-4 は例外）。また、ほとんどのモデルはバッファオーバーフローの課題でも0点だった。著者らは、LLM が自律的にエクスプロイトを生成できるようになるにはさらなる研究が必要だが、エクスプロイト能力は一般的なコーディング能力とともに向上する可能性がある、と結論づけている。

## 先行研究との関係

著者らは CyberSecEval 2 を、LLM のセキュリティ知識を問う多肢選択式のベンチマークと対比している。著者らによれば、それらは実証された能力や脆弱性ではなく、質問に答える能力を測るものである。また、要約、分類、固有表現認識のタスクを加えたベンチマークとも対比しており、その焦点は依然として主に情報検索と自然言語処理にあると述べている。脆弱性発見のために LLM を外部知識と組み合わせるフレームワークは自分たちのものにより近いとしつつ、CyberSecEval 2 はテスト対象のシステムがどのように構築されているかに依存せず、脆弱性発見ではなくエクスプロイトをエンドツーエンドで評価する点が異なると指摘している。著者らは自分たちの貢献を、LLM の実証されたリスクと能力についての最も広範な評価のセットであり、それら他のフレームワークを補完するものとして位置づけている。
