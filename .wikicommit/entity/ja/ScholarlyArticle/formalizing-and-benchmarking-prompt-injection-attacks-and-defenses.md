「Formalizing and Benchmarking Prompt Injection Attacks and Defenses」（プロンプトインジェクション攻撃と防御の形式化とベンチマーク）は、[[DefinedTerm/prompt-injection|プロンプトインジェクション]]に形式的な定義と共通のベンチマークを与えることを目指す論文である。論文の言葉によれば、プロンプトインジェクション攻撃とは、*LLM 統合アプリケーション*（大規模言語モデル（LLM）をバックエンドとして使うアプリケーション）の入力に悪意のある指示やデータを注入し、攻撃者が望む結果を出力させることを狙うものである。著者らは自らのフレームワークを、これらの攻撃を形式化した初めてのものと位置づけ、それを用いて5つの攻撃と10の防御を定量的に評価している。

この論文は arXiv に 2310.12815 として cs.CR で投稿されており、第5版は2025年11月12日付で、CC BY 4.0 ライセンスで公開されている。著者は Pennsylvania State University と Duke University の Yupei Liu、Yuqi Jia、Runpeng Geng、Jinyuan Jia、Neil Zhenqiang Gong である。著者らはプラットフォームを Open-Prompt-Injection として <https://github.com/liu00222/Open-Prompt-Injection> で公開している。

## 扱う問題

LLM 統合アプリケーションは、モデルに何をすべきかを伝える*指示プロンプト*と、モデルが処理する*データ*とをバックエンドの LLM に問い合わせることでタスクを完了する。データは多くの場合、履歴書やウェブページなどの外部ソースから来る。データが外部のものであるため、攻撃者はそれを操作できる。論文が全体を通じて用いる例は、履歴書の自動選考である。応募者は、モデルに指示を無視して「yes」と答えるよう伝えるテキストを（たとえば人間に見えないよう白地に白い文字で印字して）付け加えることで、誤って適格と扱われる可能性がある。著者らは、既存の研究論文やブログ記事はほとんどがケーススタディであり、攻撃と防御を形式化するフレームワークも、それらの包括的な評価も欠けていたため、新たな攻撃や防御を設計するのは難しく、攻撃がどれほど深刻で防御がどれほど機能するのかも不明確だったと論じている。

## フレームワーク

論文は、ユーザーが実行したいタスクである*ターゲットタスク*（*ターゲット指示*と*ターゲットデータ*を持つ）と、攻撃者が選ぶ*注入タスク*（*注入指示*と*注入データ*を持つ）を定義する。その定義によれば、プロンプトインジェクション攻撃とは、アプリケーションがターゲットタスクの代わりに注入タスクを遂行するようにターゲットデータを改変するものである。攻撃者は、データに任意のテキストを追加することはできるが、指示プロンプトを変更することはできず、指示プロンプトやバックエンドの LLM といったアプリケーションの内部も知らないと仮定される。

このフレームワークでは、異なる攻撃とは、ターゲットデータ、注入指示、注入データから*侵害されたデータ*を構築する異なる方法である。論文は既存の攻撃がその特殊なケースであることを示し、それらを組み合わせて新たな攻撃を作っている。

| 攻撃 | 侵害されたデータの構築方法 |
| --- | --- |
| Naive Attack | ターゲットデータの後に注入指示と注入データを付け加える |
| Escape Characters | 最初に改行などの特殊文字を挿入し、文脈が変わったとモデルに思わせる |
| Context Ignoring | それまでの指示を無視するようモデルに伝える*タスク無視テキスト*を挿入する |
| Fake Completion | ターゲットタスクへの偽の応答を挿入し、そのタスクが完了したとモデルに思わせる |
| Combined Attack | エスケープ文字、偽の応答、タスク無視テキストを組み合わせる。著者らがこのフレームワークを用いて設計した攻撃 |

論文は10の既存の防御を、指示プロンプトを設計し直したりデータを前処理したりしてターゲットタスクが引き続き遂行されるようにする*予防型*の防御と、データが侵害されているかどうかを判定する*検知型*の防御に分類している。著者らは、そのうちの2つ（言い換えと再トークン化）とパープレキシティに基づく検知を、いずれも元はジェイルブレイクプロンプトに対して設計されたものだったが、プロンプトインジェクションへと拡張した。また、選んだ偽陽性率のもとでクリーンなデータからパープレキシティ検知器のしきい値を設定する原理的な方法を提案している。

## どのように評価したか

ベンチマークは、GPT-4（デフォルト）や PaLM 2 から Llama-2-7b-chat や InternLM-Chat-7B までの10の LLM と、7つの自然言語タスク、すなわち重複文検出、文法訂正、ヘイト検出、自然言語推論、感情分析、スパム検出、要約を用いる。各タスクは標準的なデータセットから取られ、ターゲットタスクとしても注入タスクとしても使われるため、49の組み合わせになる。攻撃は、攻撃下での注入タスクにおけるモデルの性能である*攻撃成功値*（attack success value, ASV）と、攻撃下での応答を、注入タスクを直接問われたときにモデルが返す応答と比較する*一致率*（matching rate, MR）によって測定される。防御は、攻撃がないときのターゲットタスクの性能によっても測定され、検知型の防御は偽陽性率と偽陰性率によっても測定される。

## 要点

- 5つの攻撃はすべて有効だった。GPT-4 での49のタスクの組み合わせの平均で、ASV は Naive Attack の0.62から Combined Attack の0.75までの範囲にあり、Fake Completion が0.70で2位だった。
- Combined Attack は、GPT-4 と PaLM 2 の両方で、ほぼすべてのターゲットタスクと注入タスクの組み合わせにおいて他の攻撃を上回った。著者らはこれを、戦略を組み合わせることで攻撃の成功率が高まることを示すものと受け止めている。
- 10の LLM と49の組み合わせの平均で、Combined Attack は ASV 0.62、MR 0.78 に達した。
- 攻撃の有効性はモデルのサイズと正の相関を示した（ASV で Pearson 相関 0.63、MR で0.64）。著者らは、より大きなモデルほど指示によく従うため、より脆弱になるのではないかと推測している。
- 指示プロンプトにターゲットタスクのインコンテキスト例を加えても、Combined Attack にはほとんど効果がなかった。
- 十分な予防型の防御はなかった。どの防御も ASV と MR を高いまま残すか、攻撃がないときのターゲットタスクでの有用性を損なうか、あるいはその両方だった。たとえば言い換えは、ターゲットタスクの性能を平均0.14下げた。
- 十分な検知型の防御もなかった。パープレキシティに基づく検知は、侵害されたデータも依然として良好なテキストとして読めるため、ほとんどの攻撃を見逃した。応答に基づく検知は、ターゲットタスクが分類タスクでない場合や注入タスクと一致する場合に失敗した。単純な LLM ベースの検知は、クリーンなデータの大きな割合に誤ってフラグを立てた。既知回答検知（known-answer detection）は Combined Attack に対して最も有効だったが、他の多くのケースでは侵害されたデータの大きな割合を見逃した。

## 限界と今後の課題

著者らは、既存の攻撃はすべてヒューリスティックに依拠していると指摘し、このフレームワークを使って最適化に基づく攻撃を設計することを提案している。防御としてファインチューニングを探ることを提案しつつ、ファインチューニングしたモデルでも学習時に考慮されなかった攻撃には屈しうると注記している。また、攻撃が検知された後にクリーンなデータを*復元*する方法が文献に欠けていること、そして検知だけではアプリケーションは依然としてタスクを完了できず、サービス拒否に等しいことを指摘している。既知回答検知の評価では単一の検知プロンプトを使っており、他のプロンプトやそれに対する適応的攻撃は今後の課題としている。特定のタスクのために指示チューニングされていないモデルをファインチューニングする Jatmo のような、同時期に提案された防御は評価されていない。

## 他の研究との関係

論文は、被害者が LLM 統合アプリケーションのユーザーであり、攻撃者がアプリケーションにアクセスすることなくデータを細工するという自らのシナリオを、アプリケーションの悪意あるユーザーが攻撃者となってアプリケーションの非公開の情報を漏洩させる攻撃と区別している。また、プロンプトインジェクションをジェイルブレイクとも区別している。ジェイルブレイクは、タスクが安全でないためにモデルが拒否するプロンプトに摂動を加えて、モデルにそのタスクを実行させるものであるのに対し、プロンプトインジェクションは、ターゲットタスクの代わりに攻撃者が注入したタスクをモデルに実行させるものであり、そのタスクは安全な場合も安全でない場合もある。
