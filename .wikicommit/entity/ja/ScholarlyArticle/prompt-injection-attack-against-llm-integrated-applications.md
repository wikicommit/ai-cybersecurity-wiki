「Prompt Injection attack against LLM-integrated Applications」（LLM 統合アプリケーションに対するプロンプトインジェクション攻撃）は、LLM を基盤として構築された実際の商用アプリケーションに対する[[DefinedTerm/prompt-injection|プロンプトインジェクション]]（悪意あるユーザーが有害なプロンプトを用いて大規模言語モデル（LLM）の元の指示を上書きすること）についてのセキュリティ研究である。まず既存のインジェクション手法をそうしたアプリケーション10個で試し、それらがなぜほとんど失敗するのかを説明したうえで、従来の Web インジェクション攻撃に着想を得たブラックボックス型の攻撃手法 HouYi を提案し、36個のアプリケーションで評価している。

この論文は arXiv に 2306.05499 として cs.CR カテゴリで投稿されており、このページが依拠するのは2025年12月29日付の第3版で、CC BY 4.0 ライセンスで公開されている。12人の著者は Yi Liu、Gelei Deng、Yuekang Li、Kailong Wang、Zihao Wang、Xiaofeng Wang、Tianwei Zhang、Yepang Liu、Haoyu Wang、Yan Zheng、Leo Yu Zhang、Yang Liu で、所属はグリフィス大学、南洋理工大学、ニューサウスウェールズ大学、華中科技大学、インディアナ大学ブルーミントン校、南方科技大学、天津大学である。

## 取り組む問題

論文の説明によれば、LLM 統合アプリケーションは、サービス提供者があらかじめ書いておいたプロンプトでユーザーの入力を包み（たとえば、事前に定義された指示の中のプレースホルダーにユーザーの質問を入れる）、組み合わせたプロンプトを LLM に渡す。出力はさらに処理されることがあり、外部 API の呼び出しなどの動作を引き起こしうる。著者らは、こうしたアプリケーションで最も強力になるプロンプトインジェクションが、最近 OWASP によって LLM 関連の危険の第1位に挙げられたこと、しかし既存の攻撃は試行錯誤で見つけられた発見的なプロンプトを用いており、その背後の仕組みはよく理解されていなかったことを指摘している。

この研究の脅威モデルは、アプリケーションの公開サービスエンドポイントを通じてのみアプリケーションとやり取りし、入力を自由に操作でき、その内部（事前に書かれたプロンプト、アプリケーションの構造、背後の LLM）にはアクセスできないが、応答からある程度の情報を推測できる敵対者である。フロントエンドの欠陥や、アプリケーションが参照する外部リソースのポイズニングといった、他の脆弱性を通じた攻撃は対象外としている。

## 行ったこと

**予備調査。** 著者らは既存のプロンプトインジェクション攻撃を3種類に分類している。

| 種類 | 論文の説明による仕組み |
| --- | --- |
| 直接インジェクション | 敵対者がユーザー入力に悪意あるコマンドを付け加える |
| エスケープ文字 | 敵対者が改行やタブなどの文字を注入してプロンプトを壊す |
| コンテキスト無視 | 敵対者が、それまでのコンテキストを無視して次に来る内容に従うよう LLM に指示する文を注入する |

著者らはこれらを、Supertools コレクションの5つのカテゴリ（チャットボット、文章作成アシスタント、コードアシスタント、ビジネス分析、クリエイティブ生成）からそれぞれ2つずつ選んだ10個の商用アプリケーションに適用し、3つの簡単なテスト質問をそれぞれ5回繰り返した。

**HouYi。** 中国神話の弓の名手にちなんで名付けられたこの手法は、注入する各プロンプトを3つの構成要素から組み立てる。

| 構成要素 | 目的 |
| --- | --- |
| フレームワーク構成要素 | アプリケーションの通常の流れに沿うプロンプト。インジェクションを検知されにくくし、アプリケーションの形式チェックを通過させる |
| セパレーター構成要素 | 事前設定されたコンテキストと後続部分を切り離すプロンプト。LLM が次の入力をデータではなくコマンドとして扱うようにする |
| ディスラプター構成要素 | 敵対者の目的を実行する悪意ある質問 |

HouYi は3つのフェーズで動作する。まずアプリケーションの内部コンテキストを推測する。アプリケーションのドキュメントにある質問例を実行して回答を記録し、それを LLM に分析させて、アプリケーションの目的、尋ねられる質問の種類、入力や出力の形式を把握する。次に3つの構成要素を生成し、フレームワークとセパレーターは LLM に書かせる。セパレーターには3つの戦略を用いる。構文ベース（エスケープシーケンス）、言語切り替え（フレームワークとセパレーターをある言語で書き、ディスラプターを別の言語で書く）、意味ベースの生成（直前のタスクを論理的に締めくくる文。たとえば推論の要約を求める、無視すべき特定のタスクを名指しする、インジェクションを追加のタスクとして提示する）である。最後に各応答を LLM で評価し、失敗した場合は新しいフレームワークと新しいセパレーター戦略を試し、成功した場合はそれらを保持して次の悪意ある目的に進む。

著者らは HouYi を約2,150行の Python で実装し、36個のアプリケーション（予備調査の10個と、Supertools からさらに26個）でテストした。フィードバックの推論とフレームワークの生成には GPT-3.5-turbo を用いた。5つの攻撃シナリオ（プロンプトの漏洩、コード生成、コンテンツ操作、スパム生成、情報収集）を用い、それぞれ5回実行して、各結果を手作業で検証した。プロンプトインジェクションを実行できたアプリケーションを脆弱とみなし、インジェクションによって引き起こされたサーバーエラーは成功に数えなかった。

## 要点

- 既存のプロンプトインジェクション手法は、予備調査の10個の商用アプリケーションに対して目立った効果を上げなかった。著者らは、そのうち2つで部分的に成功した攻撃しか達成できなかったと報告しており、観察された成功例でさえ説得力のある証拠ではないと判断した。
- 予備調査は、失敗の原因をアプリケーションの3つの特徴に帰している。多くのアプリケーションはユーザー入力を答えるべき質問ではなく分析すべきデータとして扱うこと、一部は入力と出力の形式を強制しており、それが構文ベースのサニタイズのように働くこと、そして一部は応答時間制限のある多段階の処理を用いるため、操作された出力が表示されないことがあることである。
- 論文は、インジェクションの成功は、悪意あるペイロードをデータではなく質問として LLM に読ませるよう欺けるかにかかっていると論じ、ペイロードが直前の構文を終端させる SQL インジェクションやクロスサイトスクリプティングになぞらえている。
- HouYi はテストした36個のアプリケーションのうち31個で少なくとも1回の攻撃に成功し（論文は86.1%の成功率も報告している）、Notion を含む10のベンダーが脆弱性を認めた。
- 攻撃できなかった5つのアプリケーションは、汎用ではなくドメイン特化型の LLM を使っていたか、LLM の出力を複数の内部ステップで処理していたか、LLM を音声合成（text-to-speech）モデルと組み合わせていた。
- アブレーション研究では、構文のみのセパレーター戦略が最も効果が低く、意味のみの戦略が最も良い結果を示した。一方、言語切り替えは他の変種が取りこぼした1つのアプリケーションで成功した。著者らが3つすべてを組み合わせていることを確認した完全版の HouYi は、概して単一戦略の変種を上回った。
- 論文は2つの帰結を挙げている。アプリケーションの内部プロンプトを露出させ、製品を容易に複製可能にするプロンプトの漏洩と、攻撃者が提供者の費用で提供者の LLM を自分の目的に使えるようにするプロンプトの悪用である。
- 著者らが実装・評価した6つのプロンプトレベルの防御（instruction defence、post-prompting、ランダムシーケンスによる囲い込み、サンドイッチ防御、XML タグ付け、別の LLM による評価）は、著者らの手作業による検査では、いずれも HouYi によって回避されうるものだった。

## 2つのケーススタディ

論文が名前を挙げているのは、提供者が脆弱性を認めて公表を許可したアプリケーション（Notion、Parea、WriteSonic）だけで、それ以外は匿名化した別名で言及している。

- **WriteSonic のプロンプト漏洩。** 著者らは言語切り替え戦略を使い、論文が20万人を超えるアクティブユーザーを持つと説明する AI 文章作成アシスタントの WriteSonic に、その内部プロンプトを明かさせた。漏洩したプロンプトから模擬アプリケーションを作ったところ、その回答は WriteSonic の回答と驚くほど似ていた。WriteSonic の開発者は漏洩とその影響を認めた。
- **Parea のプロンプト悪用。** Parea は ChatGPT の回答を改善するためにユーザーの質問を言い換える。修正内容の説明を求める意味ベースのセパレーターを付け加えることで、著者らは Parea に任意の追加タスクを実行させることができた。Parea は無料であるため、著者らは開発者が被りうる損失を1日あたり259.2ドルと見積もっている。これは毎分90,000トークン、GPT-3.5-turbo の1,000トークンあたり0.002ドル、1,440分から算出したものである。また、ほかに30のアプリケーションが同様の悪用を受けうると報告している。Parea の開発者は脆弱性を認めた。

## 著者らが述べる限界

HouYi による情報抽出の結果は、漏洩したプロンプトが LLM のハルシネーションである可能性があるため、ブラックボックスの立場からは事実として検証できない。そのため著者らは代わりにサービス提供者に結果を確認した。成功はシナリオによってばらつきがあり、その原因は LLM の出力に固有の一貫性のなさ、一部のアプリケーションにおける不十分なエラー処理、そして他のアプリケーションにおける出力の長さと形式の制限である。3つのセパレーター戦略は、考えうる手法の表面をなぞったにすぎない可能性が高いと著者らは書いている。また、アプリケーションとその背後の LLM は変化するため、一部の脆弱性は後になって再現できないかもしれない。

## 先行研究との関係

論文は自らを Perez と Ribeiro による先行研究と対比させている。論文の報告によれば、この先行研究は GPT-3 とそれを基盤とするアプリケーションがプロンプトインジェクションに対して脆弱であることを示した。著者らは、それと比べて、より広範な実際のアプリケーションにわたって攻撃を引き起こす戦略とプロンプトパターンを体系的に探究していると述べている。論文は、ユーザーが直接与える自らのインジェクションを、敵対者がアプリケーションの取得するインターネット上のリソースにペイロードを仕込む間接プロンプトインジェクションと区別しており、後者を Greshake らに帰したうえで、自らの脅威モデルの対象外としている。また、プロンプトインジェクションを、論文が概観する他の LLM のセキュリティリスク（ハルシネーションとジェイルブレイク）と並べて位置づけ、より広い観点からはバックドア攻撃とモデルハイジャック攻撃をプロンプトインジェクションに分類している。
